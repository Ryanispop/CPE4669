Design

Our program is a simplified Dynamo-style key-value store written in Go. It starts five separate server processes on localhost. Each stores its own records in memory. One coordinator handles client operations and the hash ring. Each physical server has four virtual nodes, so the starting ring has twenty positions.

FNV-1a hashes keys and virtual-node names into 64-bit positions. Virtual-node positions are calculated once and kept sorted. To place a key, we find the first position at or above its hash, then walk clockwise, wrapping around at the end. We select three different physical servers. The first is the primary and the other two are replicas. Keys must be ASCII and at most twenty characters.

Membership and coordination

Every 200 ms, a server advances its heartbeat and exchanges membership tables with a random configured peer using HTTP and JSON. Only a larger heartbeat refreshes the observation time. After two seconds without progress, a peer is considered unavailable. The coordinator polls these gossip tables and applies the timeout. A temporarily failed server remains on the ring.

There is no consensus algorithm. The coordinator makes ring changes and processes client operations one at a time. Server data and membership maps use a mutex because gossip and HTTP handlers run concurrently. The worker peer list is static: after permanent removal, Server2 remains failed in their membership views, but is removed from the coordinator's routing.

PUT, GET, and recovery

Put assigns an increasing version and writes the same record to each available owner. It reports success if at least one owner accepts the write. Get reads available owners and returns the highest version. This prevents an older primary copy from hiding a newer replica.

Temporary recovery scans the available peers and copies missing or newer records that the returning server should own. The server stays unavailable to clients until this finishes. Permanent removal builds a ring without that server's virtual nodes, copies data from survivors to the new owners, then commits the ring change. It refuses removal if fewer than three servers would remain. Adding a server to a populated ring also copies data to its new owners.

Running the program

./run.sh demo
./run.sh bench 1000 3
./run.sh test

Requires Go 1.22 or newer and Bash. No third-party Go libraries are needed. To compile directly, use go build -o lab7 .. The demo starts and stops the child processes automatically. Logs and output are saved under results/. The default virtual-node count can be changed with -vnodes.

Correctness and failure experiment

The demo inserts Maria=100, John=20, Anna=40, Tim=100, Alex=10, Lauren=30, and Thomas=50. It checks the values and all three replicas. Then it kills Server2, waits for timeout detection, and shows which replicas answer reads. Thomas is changed to 75 during the outage. Server2 restarts with empty memory and receives its current records, including Thomas=75, before reads are allowed again.

Finally Server2 is killed and permanently removed. Affected records are copied to their new owners. All seven keys are checked again, including all three stored copies and their versions. Unit tests also check ring wraparound, distinct owners, invalid keys, missing keys, unavailable owners, stale records, recovery, joining a populated ring, removal, and heartbeat progress. Tests and the race detector passed; results/tests.txt contains the result.

Performance

Each run performs 1,000 PUTs followed by 1,000 GETs. We report the median of three runs. Startup, shutdown, and the final replica scan are outside the timer; checking GET values is included. The single-server HTTP run is the baseline. Replication is min(3, server count), since one or two servers cannot hold three distinct copies. All configurations use the same keys, but additional copies increase the work.

T1/Tn is conventional speedup. Tn/T1 is the time ratio written in the lab instructions. All client operations and replica requests are sequential. More servers do not create parallel client work, and more replicas add HTTP requests, JSON serialization, mutex locking, and network latency. Background gossip and failure detection add work too. Four virtual nodes do not guarantee even load for a small workload. These costs explain why additional servers may take longer. All processes share one machine, so these measurements describe localhost latency rather than multi-machine throughput.

Simplifications and conclusion

This version uses a central coordinator, increasing version numbers, and full record scans instead of Dynamo's decentralized coordination, vector clocks, and optimized anti-entropy. It has no durable storage, quorum guarantees, or concurrent client coordination. Recovery runs while client writes are paused. The coordinator and its counter are not recovered after a crash. Losing all current copies loses a key. A single acknowledged copy can be lost before repair. Wall-clock heartbeats assume one host without clock changes. Network-partition reconciliation is not implemented.

The experiments show that replicas allow operations to continue during a server outage, recovery restores missed writes, and permanent removal restores three owners. Adding servers does not automatically make a small sequential workload faster.
